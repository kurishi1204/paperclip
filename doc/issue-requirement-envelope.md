# First canary Issue requirement envelope

This is the read contract for the first `internal_docs_only` Issue canary. A caller implementing the seven-field `RequirementEnvelope` contract may read `GET /api/issues/:id/requirement-envelope`. It returns exactly `id`, `companyId`, `revision`, `task_kind`, `requirements_text`, `accepted_requirements`, and `native_document_complete`. There is no pagination, conditional 304 response, ETag, or response cache. `Cache-Control: no-store` is mandatory.

The whole Issue `description` must be a JSON object with exactly these four keys:

```json
{
  "task_kind": "internal_docs_only",
  "requirements_text": "Write an internal note.",
  "accepted_requirements": ["Internal circulation only"],
  "native_document_complete": true
}
```

The text and each acceptance item must be nonempty strings after whitespace is removed. Missing, extra, duplicate, malformed, or unsupported fields produce HTTP 409 with `code: requirement_projection_hold`. This strict description format is **only** the first canary. It does not define a general Paperclip Issue format or authorize interpretation of arbitrary Markdown, comments, documents, attachments, or approvals as accepted requirements. Existing Issues with comments or other unsupported material hold; a successful projection does not establish acceptance or dispatch.

The route holds the Issue row lock and checks authorization, the active Run binding, native requirement child counts, unsupported graph/governance material, and the complete JSON description in one database transaction. The actor must be the assigned agent using a runtime-issued agent JWT. Its Run ID must match the Issue's server-owned execution lock and the Run's claimed wake receipt. The receipt must identify a normal Issue creation, assignment update, or status-change wake and contain only the canonical task context for this canary. Before checkout, the Run context must equal that canonical task context; direct managed Anthropic account attribution is accepted only after checking its typed agent and responsible-user binding. During checkout, heartbeat adds workspace, environment, adapter, and execution metadata. It writes a digest of the **entire** JSONB runtime context into the server-owned claimed wake receipt in the same transaction as the Run context. The route compares the complete context with that digest, so any subsequently added instruction, execution control, or task identity change holds instead of silently becoming a projected Run. This is a binding for the canary GET, not a grant of requirement authority to runtime metadata: requirement text comes only from the locked Issue description. A changed claimed wake receipt also holds. Before checkout, the Issue may be `backlog` or `todo` with no checkout lock and with `executionRunId` bound to this already-running Run. After checkout, both Run locks must match that same Run and the Issue must be `in_progress`. Another company, agent, Run, or credential class cannot read this projection. Two active Runs claiming the same Issue hold the canary. A parent or child Issue, linked project or goal, watchdog (including an inactive one), work product, approval, plan decomposition, execution decision, recovery action, or any currently versioned native child material holds the canary rather than being silently omitted. The route inspects the migrated database catalog for all direct Issue references, including future columns; any populated reference other than the checked local lease for the active Run holds it. Other execution settings and nonstandard Issue origins hold it.

When the managed heartbeat activates a continuation identity, the Issue's identity ID must equal the current Run's active identity ID. The identity record must belong to the same company and Run, be accepted, have the same responsible user and wake cause, and carry no message or parent context. A mismatch holds the canary. The local environment lease created during execution is allowed only while active, ephemeral, and bound to the same company, Issue, and Run. A lease for another Run or provider holds. The route also verifies the exact set of applied SQL migration hashes through migration 0313. An unreviewed added or replaced migration holds the canary, even if the new schema is unrelated to Issues. Releasing a later schema requires reviewing its new paths for instruction material and updating this bound and its fault tests.

`revision` is a SHA-256 digest of the fixed envelope schema marker, Issue and company IDs, the Issue title, and the four accepted description fields in a fixed JSON key order. The title can affect task meaning even though it is not returned in the seven-field envelope, so editing it changes the revision. The digest does not use `issues.revision`, status timestamps, or the all-row snapshot digest: those change during checkout and ordinary status updates. A description requirement edit also changes this revision. The caller must still reread after checkout and immediately before each effect; a repeated GET is a guard, not an atomic compare-and-swap with a later external call.

This GET is read-only. It neither reserves an outbox intent nor invokes Orca or any other external effect. Durable outbox reservation, same-transaction comparison, dispatch, and authoritative external readback belong to a later phase and need their own acceptance evidence. This endpoint does not establish company request acceptance, worker dispatch, result QA, or business acceptance.

Implementation and local verification used Codex as the fallback because Claude was not signed in. The exact model ID of this Codex agent was not exposed by the runtime and remains unverified. Independent Claude review, PR CI, merge, main CI, and live external acceptance remain separate gates.
