# Fresh Paperclip Runner Task admission

This is the local development contract for fresh `enqueueWakeup` admissions. It does not cover retry promotion, recovery producers that insert Runs directly, provider execution, or production acceptance.

Before changing a wake admission, trace four layers in the same source revision:

1. Entry: identify the route or caller and the `heartbeatService.enqueueWakeup` branch that receives its Task reference.
2. Callee contract: read `assertPaperclipRunnerTaskEligibility` in `server/src/services/native-runtime/runtime-mode.ts` and its execution-time use by `resolveNativeRuntimeMode`. Preserve the separate agent, provider, rollout, assignment, dependency, and budget checks.
3. First side effect: follow provider normalization (an agent update and activity record), then any skipped, deferred, or coalesced wake receipt, and finally the fresh `heartbeatRuns` insert in each scoped/unscoped branch of `server/src/services/heartbeat.ts`. Check prior durable receipts, retry and reconciliation successor replay, and coalescing before claiming a new Run would be minted. The fresh Task predicate runs after legitimate replay and before new defer, coalesce, or Run minting.
4. Minimal comparison: run `server/src/__tests__/heartbeat-native-task-preflight.test.ts` against an owned embedded PostgreSQL. A standard Task and an unscoped direct adapter must queue normally. For a scoped runner, change only `workMode` from `standard` to `skill_test`; for the unscoped runner, omit the Task. A direct adapter without a Task is a separate adapter-type control, not a one-variable Task comparison. Ineligible ordinary manual user wakes must reject before both a new Run and a queued wake receipt; an already accepted durable user input and a non-user wake must return null with one terminal skipped receipt. Existing execution-wait receipts are retired only after their company, agent, actor and Task binding is revalidated. Count every selected test, failure, and skip; a skipped database suite is not acceptance. On the macOS arm64 acceptance host, a failed embedded-Postgres support probe makes this suite fail explicitly. Other platforms retain the repository convention of skipping when the optional embedded database is unavailable.

The enqueue check reuses only the Task clause. `payload.taskId` is normalized to the scoped Task; `taskKey` alone only addresses a session and cannot supply execution Task authority. Execution still repeats the complete runtime resolver under current state. The scoped gate reads the current adapter type after locking the issue, but does not lock the agent row in the reverse order; a concurrent adapter-type change remains an execution-time recheck case. A newly ineligible durable user input gets one terminal skipped receipt under its existing request ID; ordinary manual user wakes still receive 409. The saved execution-wait receipt retains a machine-readable reason and message, but the current issue view projects `executionWait` only for deferred receipts, so this does not prove an on-screen explanation for a skipped receipt. An already admitted retry or reconciliation successor replays before the fresh gate. If a pending reconciliation has no successor and its Task becomes ineligible, the bound action is invalidated under the issue/action locks to stop repeated delivery attempts. The normal timer scheduler claims and advances `lastHeartbeatAt` before calling `enqueueWakeup`; direct timer calls outside that scheduler have not been qualified by this test. Existing persisted-run recovery, prior durable receipt replay, and other direct Run producers need separate analysis and must not be reported covered by this fresh-wake gate.
