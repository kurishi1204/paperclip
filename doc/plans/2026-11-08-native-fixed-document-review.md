# Fixed document QA through the dedicated task tool

An employee could discover the interaction REST endpoint but could not create a named document review through it: generic `call_api` deliberately rejects interaction mutations. The dedicated `request_human_input` tool did not accept or forward a reviewer, so callers fell back to separate review tasks.

For standard-mode business tasks the dedicated tool now accepts an optional `addresseeAgentId` on a confirmation bound to the exact saved current-task documentId/key/revisionId. The normal interaction service checks company membership, independent/invokable addressee, current document identity and resolver governance. Under the creation locks it also rejects a document creator/latest editor as reviewer and a human-only company cap, rather than creating an unusable card. It receives no caller-supplied or synthesized resolver-policy override. The reserved plan document, planning mode, governed actions, ordinary human questions and Ask mode cannot use the named-review option. Existing human-only decisions keep their resolver restriction. Generic REST creation and decision escapes remain denied. A pending employee document review is isolated from unrelated confirmation replacement and the periodic sibling-card sweeper, and from unrelated current or historical human comments even on older opt-in cards. Reviewer status and reporting-chain eligibility are rechecked under shared row locks in the insertion transaction. Same document/revision/reviewer requests with another key return an explicit conflict pointing at the existing review; the original stable key remains idempotent across a fresh authorized run without a second created event or any change to the original sourceRunId. Stale-document and explicit lifecycle expiry retain their existing paths.

The scenario simulator does not implement live employee review dispatch. It returns an explicit unsupported result for a named reviewer instead of silently creating a human card without that reviewer. Live/scenario descriptors and generated catalog/contract projections are updated through their normal generators.

Qualification keeps old failed attempts, tests the actual saved addressee against the old authority, and exercises the real isolated database/HTTP fixture. Production acceptance still requires same-head independent review, normal CI/build and an actual existing-employee fixed-version QA handoff; local checks alone do not complete it.

The dedicated tool uses the existing server scheduler after commit, with the canonical interaction-pending receipt. Same-key requests are rechecked under the issue lock. Native review creation shares its actor-state lock so concurrent reviewers do not take conflicting exclusive actor locks.

The existing created-activity record also stores a server-owned wake intent in the same transaction as the card and semantic receipt. The normal scheduler reconciles undelivered intents after restart. Any existing queue receipt, including an unresolved failure, prevents re-enqueue; current document admission and the normal issue lock remain authoritative. Delivery failures are returned after unrelated queued work proceeds.

## Author-selected source inclusion for one-document QA

A confirmation that only links to the request and result cannot be evaluated by a reviewer restricted to one fixed document. When the native `write_document` definition advertises `includeDocuments`, the author can select current documents on that same task by document ID, key, revision ID, UTF-8 byte count and SHA-256. The shared write authority reads those fixed originals and embeds their complete bodies beside the author confirmation in one saved Markdown document. It returns source byte ranges and the saved target revision/digest after an exact transactional readback. The author remains responsible for choosing sufficient material; byte equality does not establish completeness, independent QA or adoption.

The existing issue lock serializes source updates. Stale, foreign, duplicate, self-referential, changed or oversized material is rejected without truncation. Existing mutation receipts preserve same-key replay and reject changed input; an unknown write or review outcome must be reconciled through its original receipt. The caller reads the saved target and submits only its exact revision through the existing dedicated named-review path. Reviewer scope and human-only decisions are unchanged. Ordinary writes remain compatible. Scenario and command-only bindings that cannot perform native inclusion reject it explicitly.

This is an unadopted source candidate until normal CI, same-head review and deployment conditions are met. An existing business processed through the old live tools is not evidence that the new inclusion path has been used.
