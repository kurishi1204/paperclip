# Conditional board review start

Use normal `PATCH /api/issues/:id` with `boardReviewExpected: {revision, statusVersion, stageId, reviewerAgentId}` to start the first review of a completed execution. The caller must be the board, the issue must still be `in_progress`, and its execution policy/state must be unset. The normalized policy must keep that exact first review stage with one agent participant and one required approval. Empty or dropped stages are refused. The review comment is written in the same transaction as the stage; an idempotency conflict rolls back the entire start. Only `status: in_review`, `executionPolicy`, a nonempty `comment`, and optional `commentClientRequestId` accompany this precondition.

The server checks the version and absence of active issue runs before preparing the transition, then again under the issue row lock in the transaction that writes the pending stage. A stale request fails with 409. This path does not stop the old worker or cancel a run. Closed execution workspaces require a separate reopen action. Dispatch and run-bound QA verdicts retain their existing contracts.

`expectedRevision` remains the title/description contract; it does not authorize review transitions. A successful conditional start is not an independent QA result or owner business acceptance.

## Deployment follow-up

The Codex QA installer was observed creating root directories as 0700 under a root umask of 077 despite requesting 0755. The existing dedicated directories were repaired to root-owned 0755 and UID501 traversal and `codex --version` were verified. A future installer change must apply explicit descriptor-based chmod to newly created directories and test creation under umask 077 plus execution by the actual service UID. Do not remove quarantine or relax ownership/write restrictions.

## Resume a blocked pending QA

Set `boardReviewExpected.resume: true` with the current revision, statusVersion, stageId and reviewerAgentId. Send only `status: in_review`, the resume comment and optional commentClientRequestId. Do not send a new execution policy. The server accepts only blocked issues retaining that exact pending review stage, assigned to that same agent, with no active issue Run. It restores the same stage and commits its comment atomically. The normal assignment dispatch then owns execution; callers must join its Run rather than create a second wake.

## Policy-only preparation for independent approval

The separate `POST /api/issues/:id/native-review-policy` entry does not extend ordinary PATCH `expectedRevision`. An authenticated active company owner session may request `operation: amend` with `replacementAgentId` and the explicit `oldApprovalDisposition: withdraw_for_author_resubmission`. Required preconditions are `expectedIssueRevision`, `expectedStatusVersion`, `expectedDecisionId`, and the SHA256 pins `expectedPolicySha256`, `expectedCardsSha256`, `expectedDocumentsSha256`. Pins use canonicalNativeJson; cards are the complete union of pending cards and cards naming the current decision, ordered by id with dates serialized as ISO strings; documents are the original current non-bookkeeping binding ordered by key/id. No caller-supplied wake context or document binding is accepted.

This narrow entry supports an in-review native completion with exactly one agent QA and one agent approval stage. It changes only the approval participant's agent id. QA, quorum, stage/participant ids, assignee, status and status version remain unchanged. The issue lock, active owner membership, applied decision, original source author, exact pending cards and delivered binding effects, current document set and the original full-history author exclusion are checked before persistence. A missing document revision, active execution, unresolved delivery, or unproved terminal receipt refuses the operation. Historical failure is not converted to successful completion. Positive terminal qualification is deliberately conservative and may require original result reconciliation; this entry is not a general ban on other local preparation.

Keeping the removed approval card pending would obstruct even the next decision: the original accept consumer refuses completion while any issue card is pending. Migration therefore explicitly marks only that card cancelled with the existing administrative `withdrawn` result and the owner's identity, in the same transaction as the policy CAS. It preserves its payload, binding, original delivery effect and history; it does not record a QA verdict. The original QA card remains pending and can request changes through its separately qualified original return/decision entry. The assignment reader also refuses pending cards belonging to a participant removed from the current policy. Only a later original-author submission creates new cards and deliveries. No wake or replacement card is produced by the amendment. The original decision still cannot finish by treating a withdrawn required approval as accepted.

`operation: restore` takes the same current pins and `amendmentActivityId` instead of a replacement. The same owner, original amendment audit, exact post-amendment revision/policy/card/document state and execution/result boundary must match. An intervening execution or mutation refuses restore. The final revision includes the original child-update trigger's revision bump; the caller must use the returned value, not an assumed increment. Restore writes only the recorded prior policy and a new audit; it does not resurrect the withdrawn card, accept a verdict or replay delivery. The original author's resubmission remains necessary after restore. A lost response is investigated through the audit and current revision rather than resent.

The route/service and assignment reader are a source candidate until accepted and deployed. Non-DB route checks do not establish SQL concurrency, live DB/HTTP, independent review, deployment, QA or business acceptance. Company-owner authorization to designate a technical approver and the candidate's original unresolved result boundary remain separate prerequisites to a real invocation.
